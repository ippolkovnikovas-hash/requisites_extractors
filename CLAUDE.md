# CLAUDE.md

## Проект

Локальная обработка реквизитов организации: PDF/JPG/DOCX → OCR/LLM/regex-извлечение →
редактируемая review-форма → заполненный DOCX по `shablon.docx`. Основной сценарий:
загрузка документа → ручная проверка и правка распознанных полей в форме → кнопка
«Сформировать DOCX».

## Приватность

- Реквизиты не должны уходить во внешние сервисы ни при каких обстоятельствах.
- OpenAI и любые другие внешние API/сервисы для передачи или обработки реквизитов
  запрещены — полностью исключены из кода и зависимостей.
- Ollama — только локальный endpoint, без внешних/облачных LLM-провайдеров.
- `mock`-провайдер используется только для тестов и CI.

## Секреты и `.env`

- Никогда не читать и не выводить содержимое `.env`.
- Не добавлять ключи и секреты в репозиторий, не коммитить `.env`.

## Git и деструктивные операции

- Не выполнять `git commit`, `git push`, `git rm`, удаление файлов или изменение
  Git-индекса без отдельного явного подтверждения на каждое конкретное действие.
- Не включать auto mode / автономный режим без отдельного подтверждения.

## Процесс изменений

- Перед изменением любого файла — показать план или точный diff и дождаться
  подтверждения. Не применять правки молча.
- Порядок разработки — TDD: сначала тесты, затем реализация, затем прогон
  относящихся тестов. `ImportError`/`ModuleNotFoundError` в тестах, написанных до
  реализации, — ожидаемое и нормальное состояние, не повод откатывать тесты.

## Правила валидации (обязательны для всех валидаторов проекта)

- `raw_value` всегда сохраняет исходное значение как есть — никогда не изменяется
  и не скрывается от пользователя.
- `normalized_value` — только прозрачная нормализация (пробелы, регистр,
  однозначные OCR-подмены); он не должен скрытно подменять `raw_value` в
  review-форме.
- Пустое (не заполненное) значение и введённое, но невалидное значение — разные
  состояния (`is_missing` ≠ `valid=False`); отсутствие необязательного поля не
  считается ошибкой.
- Жёсткая ошибка (`valid=False`, не `is_missing`) блокирует генерацию DOCX в
  `/generate` без явного подтверждения (`confirm_invalid`).
- `warning` показывается в форме рядом с полем, но сам по себе никогда не блокирует
  генерацию документа.
- КПП проверяется только по структуре (4 цифры + 2 цифры/буквы + 3 цифры) —
  контрольной суммы у КПП нет и не будет.
- БИК и счета: неверная длина или недопустимые символы после нормализации —
  жёсткая ошибка; нетипичный префикс и контрольный ключ — только предупреждение.
- Контрольный ключ БИК↔счёт (методика ЦБ РФ №515): для р/с используется `БИК[6:9]`,
  для к/с — `"0" + БИК[4:6]`; результат этой проверки всегда только `warning`,
  никогда не блокирующая ошибка.
- Почтовый индекс — для юридического и для почтового адреса желателен, но не
  обязателен: его отсутствие не создаёт warning и не блокирует генерацию.

## Тесты

- После каждого этапа реализации — запускать относящиеся к нему тесты.
- Перед завершением задачи — запускать полный `pytest`.
- Не снижать порог coverage и не расширять список исключений coverage (`omit`) без
  отдельного явного подтверждения.

## Артефакты и Git

- Не хранить в Git реальные загруженные документы, а также содержимое `exports/`,
  `uploads/`, `processed/`, `storage/` и логи с реальными реквизитами.
- `/generate` использует только временные файлы/`BytesIO`; результат не должен
  оставаться на диске или в репозитории после отправки ответа.
