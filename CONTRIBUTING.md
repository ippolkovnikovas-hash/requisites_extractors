# Как участвовать в разработке

Короткий документ о принятом в проекте порядке работы. Устройство приложения —

## Настройка

```bash
py -3.13 -m venv .venv
.venv\Scripts\Activate.ps1        # Windows
# source .venv/bin/activate       # Linux/macOS

pip install -r requirements/dev.txt
copy .env.example .env
```

Нужны также Tesseract с русским пакетом и Poppler — см. README. Ollama
необязательна: тесты идут на `LLM_PROVIDER=mock`.

`easyocr` ставить не нужно, если не собираетесь его использовать: он тянет torch
(~500 МБ) и вынесен в `requirements/easyocr.txt`.

## Порядок работы: сначала тест

В проекте принят TDD, и это не формальность — на нём поймана заметная часть
багов. Порядок:

1. Написать тест, фиксирующий ожидаемое поведение.
2. Убедиться, что он падает **по той причине, которую вы ожидаете**.
3. Написать реализацию.
4. Прогнать относящиеся тесты, затем весь набор.

`ImportError` в тесте, написанном раньше реализации, — нормальное состояние, а
не повод откатывать тест.

### Почему шаг 2 важен

Несколько раз тест падал не по той причине, что предполагалась, и это меняло
понимание задачи. Например, тест на перестановку ФИО падал не из-за отсутствия
логики — логика была, — а из-за того, что её результат перекрывался другим
извлекателем. Если бы шаг пропустили, «починили» бы не то.

## Проверки

Ровно эти три команды запускает CI. Все три должны проходить чисто.

```bash
pytest
ruff check app/ scripts/ tests/
black --check app/ scripts/ tests/
```

Отдельный модуль без замера покрытия:

```bash
pytest --no-cov tests/test_validators_inn.py
```

### Покрытие

Порог задан в `pyproject.toml` (`--cov-fail-under`). Сейчас 93% при фактических
94%.

Два правила, действующие без исключений:

- **Порог не понижать.** Если новый код тянет цифру вниз — писать тесты, а не
  двигать порог.
- **Список `omit` не расширять.** Он сокращается по мере покрытия и сейчас
  содержит один файл. Добавление туда чего-либо требует отдельного обсуждения.

### Проверка в чистом окружении

Если трогаете зависимости — обязательно проверьте установку с нуля. Локальное
окружение обманчиво: пакет может оказаться в нём случайно.

```bash
python -m venv /tmp/civ
/tmp/civ/bin/pip install -r requirements/dev.txt
/tmp/civ/bin/pytest
```

Именно так нашлось, что два теста импортируют `reportlab`, которого не было ни в
одном requirements-файле, — CI упал бы на первом же запуске.

## Что нельзя

Правила из [CLAUDE.md](CLAUDE.md), нарушение которых не пройдёт ревью:

- **Внешние сервисы для обработки реквизитов.** Никаких облачных LLM, API
  проверки контрагентов, справочников по сети. LLM — только локальная Ollama.
- **Внешние ресурсы в шаблонах.** Никаких CDN: приложение должно работать
  офлайн. Защищено тестами в `tests/test_offline_assets.py`.
- **Реальные документы и логи с реквизитами в репозитории.** Фикстуры в
  `tests/fixtures/` синтетические, с выдуманными, но корректными по алгоритму
  ИНН/ОГРН.
- **Секреты в коде и `.env` в Git.**

## Правила валидации

Если добавляете или меняете валидатор, соблюдайте контракт `FieldValidation`:

- `raw_value` сохраняется всегда и никогда не меняется — его видит пользователь.
- `normalized_value` — только прозрачная нормализация: пробелы, регистр,
  однозначные OCR-подмены.
- «Не заполнено» (`is_missing`) и «заполнено неверно» (`valid=False`) — разные
  состояния. Отсутствие необязательного поля ошибкой не считается.
- `reason` — жёсткая ошибка, блокирует генерацию. `warning` — не блокирует
  никогда.

Ошибкой делайте только то, в чём уверены. Контрольная сумма — ошибка.
Нетипичный префикс — предупреждение.

Подробности и таблица решений — в
[docs/architecture.md](docs/architecture.md#валидация).

## Коммиты

Формат заголовка — `type: краткое описание` в повелительном наклонении:

```
feat:  новая функциональность
fix:   исправление
chore: инфраструктура, зависимости, уборка
docs:  документация
test:  тесты
ci:    CI/CD
style: форматирование без смысловых изменений
```

В теле объясняйте **почему**, а не что: что сделано, видно из диффа. Особенно
ценно описывать найденные по пути проблемы — они и есть самая полезная часть
истории.

Форматирование выносите в отдельный коммит: механический дифф на 50 файлов,
смешанный со смысловыми правками, невозможно ревьюить.

| Что изменилось | Что обновить |
|----------------|--------------|
| Поведение, видимое пользователю | `README.md` |

отмечен сделанным, это должно быть проверяемо.
