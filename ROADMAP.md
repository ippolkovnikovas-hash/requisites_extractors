## 0. Продуктовая рамка и зафиксированные решения

Решения приняты 23.08.2026 и являются входными условиями для всего плана ниже.

| # | Решение |
|---|---------|
| Р1 | Это **локальное однопользовательское приложение**, а не сервис. Всё проектируется под запуск на машине пользователя, без сети наружу. |
| Р2 | Главный интерфейс — **web review-форма**: загрузка → правка распознанных полей → `POST /generate` → DOCX. REST API (`/api/*`) остаётся вспомогательным слоем для CLI/batch/интеграций, но не ведёт разработку. |
| Р3 | **OpenAI удаляется полностью** — код, зависимость, настройки, упоминания в документации. Остаются только `ollama` (локальный endpoint) и `mock` (тесты/CI). |
| Р4 | **Сохранение промежуточных артефактов на диск становится опциональным.** По умолчанию pipeline не пишет `processed/*_raw.txt`, `processed/*_normalized.txt` и `exports/*` — всё в памяти. Сохранение включается явным флагом для CLI и batch, где оно действительно нужно. |
| Р5 | **`omit` в coverage сокращается поэтапно**, а не расширяется. Порядок: сначала `validators/` и `core/` (цель ≥90%), затем `services/` и `web/`. Порог `--cov-fail-under` поднимается по мере готовности и не опускается. |
| Р6 | **Docker удалён из проекта.** Для десктопного приложения он требовал установки Docker Desktop и упирался в доступ к Ollama на хосте (firewall/сети WSL), не решая ни одной реальной задачи. CI будет собираться на голых GitHub-раннерах с `apt install tesseract-ocr poppler-utils`. |
| Р7 | **Целевой формат — локальный сервер + браузер:** запуск одной командой или ярлыком, Flask на `127.0.0.1`, автооткрытие браузера. Упаковка в `.exe` и нативное окно не делаются (см. §5). |
| Р8 | **Python 3.13+** — floor 3.13 (текущий `.venv`), поддерживается и 3.14. Проверено: весь стек, включая `torch`/`easyocr`, резолвится на обеих версиях (`torch 2.13.0` публикует `cp314`-колёса). |

## 1. Фактическое состояние кода

### 1.1. Что действительно работает

- **Pipeline** (`app/services/pipeline_service.py`) — сквозной проход
  routing → extraction → normalization → LLM → fallback regex → merge →
  validation → export. Оркестратор целостный, логирование по шагам есть.
- **Routing** (`routing_service.py`) — DOCX / PDF-text / PDF-scan / image /
  unsupported, с определением наличия текстового слоя в PDF.
- **Экстракторы** — `docx_extractor`, `pdf_text_extractor` (pdfplumber),
  `pdf_ocr_extractor` (pdf2image + Tesseract), `image_ocr_extractor`
  (предобработка PIL + Tesseract).
- **Структурный OCR** — `TesseractBackend.image_to_lines()` уже использует
  `image_to_data(Output.DICT)` с группировкой по `block_num`/`line_num`.
  Оба OCR-экстрактора им пользуются.
- **Fallback regex** (`fallback_regex_service.py`, ~660 строк) — самый
  проработанный модуль: контекстный поиск ИНН/КПП/ОГРН/БИК/рс/кс, разбор
  карточки контрагента, извлечение ФИО с нормализацией порядка и краткой формы,
  `merge_llm_and_fallback()` с `extracted_by`.
- **LLM-слой** — `base.py`, `mock_client.py`, `ollama_client.py` (только
  локальные провайдеры), три версионированных промпта (`v1`, `v2`, `v3`) с
  `get_prompt()`/`list_versions()`.
- **Экспортёры** — `json_exporter`, `xlsx_exporter`, `docx_exporter.fill_template()`
  (замена плейсхолдеров `'ALIAS'` в параграфах и таблицах, с учётом разбиения по runs).
- **REST API** — `GET /api/health`, `POST /api/extract`, `GET /api/result/<id>`,
  `GET /api/download/<id>/<fmt>`, единый формат ошибок `{error, code, details}`.
- **CLI** — `run_cli.py` (`process`, `batch`, `validate`, `info`),
  `batch_process.py` с отчётом CSV/JSON.
- **Тестовый фундамент** — 21 тестовый модуль, синтетические фикстуры
  (`sample_requisites.docx/.pdf`, `sample_two_pages.pdf`, `sample_with_table.docx`).

### 2.2. Правила валидации

| Правило CLAUDE.md | Факт в коде |
|-------------------|-------------|
| `raw_value` всегда сохраняется и не скрывается | В `FieldValidation` **нет поля `raw_value`** — только `value`, `valid`, `reason` |
| `normalized_value` — прозрачная нормализация | Поля **нет вообще** |
| `is_missing` ≠ `valid=False` | Поля **нет**; `validate_*` на `None` возвращают `valid=False, reason="field is null"` — пустое и невалидное неразличимы |
| `warning` не блокирует генерацию | Поля **нет**; всё сваливается в `errors` |
| Префикс БИК — только warning | `bik_validator.py`: «BIK must start with 04» → **hard error** |
| Префикс счёта — только warning | `account_validator.py`: «must start with 40/30» → **hard error** |
| Контрольный ключ БИК↔счёт (ЦБ РФ №515) — всегда warning | `validate_cross_bik_corr()` попадает в `report.errors` → **блокирует**; и алгоритм не тот (сравнение `кс[17:20]` с `БИК[-3:]` вместо расчёта контрольного ключа по `"0"+БИК[4:6]`) |
| Контрольный ключ для р/с (`БИК[6:9]`) | **Не реализован вообще** |
| Отсутствие необязательного поля — не ошибка | `validation_service.py` добавляет «X отсутствует» в `errors` для всех шести полей |
| КПП: 4 цифры + 2 цифры/буквы + 3 цифры | `kpp_validator.py` требует `isdigit()` — **буквы в позициях 5–6 отвергаются**, хотя они легальны |
| Почтовый индекс необязателен, его отсутствие не warning | Валидатора адреса нет вообще |
| `raw_value` не скрывается от пользователя | `validate_requisites()` делает `setattr(data, field_name, None)` — **затирает** исходное значение при невалидности |

### Э13. Спринт 1 разбора пайплайна OCR → реквизиты *(сделано 04.09.2026)*

Эпик открыт по итогам разбора на синтетической карточке контрагента: чистый
текст, «скан» с шумом и наклоном 0.4°, полный `run_pipeline`. Ключевой вывод —
на чистом тексте LLM извлекает все 16 полей верно и воспроизводимо (три прогона
подряд дали одинаковый JSON), а на скане тот же документ разваливается. Значит,
дефект не в модели и не в промптах, а в слое между OCR и извлечением.

- [x] **`image_to_lines()` склеивал документ в одну-две строки.** Ключ
      группировки был `(block_num, line_num)`, но `line_num` уникален внутри
      параграфа, а не внутри блока: строки разных параграфов с одинаковым
      номером сливались в одну. На карточке из пятнадцати строк получалось две,
      после чего построчный regex-слой начинал затаскивать в поле содержимое
      соседних строк. Ключ расширен до
      `(page_num, block_num, par_num, line_num)`. Задевало обе ветки — и
      изображения, и PDF-сканы: оба экстрактора зовут `image_to_lines()`.
- [x] **Жадные квантификаторы в метках полей.** `[^\n]{0,30}` после подписи
      съедал тридцать символов самого значения: «Общество с ограниченной
      ответственностью Ромашка» приходило как «тственностью Ромашка», а краткое
      наименование утекало на следующую строку документа. Воспроизводилось на
      чистом тексте, без всякого OCR. Введён `_LABEL_TAIL`: необязательное
      уточнение в скобках плюс обязательный разделитель — либо перевод строки,
      если значение стоит следующей строкой.
- [x] **Правило merge «длиннее — значит лучше».** Оно работало обратно
      задуманному: чем больше регекс перехватил соседних строк, тем увереннее
      он побеждал корректное значение LLM. Заменено на признак — наличие
      организационно-правовой формы в наименовании и отсутствие внутри значения
      меток чужих полей и длинных чисел (`_looks_contaminated()`).
- [x] **Промпт уходил в модель с `{{` и `}}`.** Шаблоны написаны под
      `.format()` и хранят экранированные скобки, а подстановка делается через
      `.replace()` — экранирование не снималось, и модель получала пример
      ответа с синтаксически битым JSON. Спасал только `format: "json"` на
      стороне Ollama.
- [x] **Поля `extra` не печатались ни одним синком** (остаток Э12). loguru
      кладёт kwargs в `record["extra"]`, а формат состоял из одного
      `{message}`. Добавлен `_format_with_extra()`; фигурные скобки в значениях
      экранируются, иначе loguru принимает их за плейсхолдеры.
- [x] **Приватность лога.** `fallback_regex_service` писал в неподключённый
      stdlib-логгер отладку с четырьмя тысячами символов документа и всеми
      реквизитами целиком. После перевода модуля на loguru это попало бы прямо
      в `logs/app.log`, поэтому одновременно заменено на имена найденных полей.
      То же сделано для трёх `logger.debug` в `pipeline_service`.

**Результат:** 543 → **553 теста**, покрытие 94.48% при пороге 93, `ruff` и
`black` чисты. Тот же скан через полный pipeline отдаёт верные `company_name`,

### Э14. Спринт 2 разбора пайплайна: устойчивость и приватность *(сделано 04.09.2026)*

Продолжение Э13 на той же ветке разбора. Все четыре пункта не требовали
входных данных от автора — этим и был выбран порядок.

- [x] **Недоступная Ollama больше не роняет весь pipeline.** `try/except
      (LLMError, LLMParseError)` оборачивает только `llm_client.extract()`, а
      не `_build_llm_client()` — опечатка в `LLM_PROVIDER` остаётся жёсткой
      ошибкой конфигурации и продолжает долетать до вызывающего кода, это
      осознанное решение, а не временная недоступность. При обрыве связи или
      неразбираемом ответе модели pipeline переходит в regex-only режим:
      пользователь получает review-форму с тем, что нашёл regex-слой (12 из
      16 полей на фикстуре проекта), а не голое сообщение об ошибке. Баннер
      «LLM недоступна: реквизиты заполнены только по regex-правилам» стоит
      первым в списке предупреждений — без него остальные warnings читаются
      неверно. `processing_meta["llm_failed"]` фиксирует режим для API и
      логов.
- [x] **Вызов Ollama стал детерминированным и структурированным.** `format`
      теперь принимает JSON Schema, построенную из
      `RequisitesData.model_json_schema(by_alias=False)` — имена полей в
      схеме совпадают с тем, что просят промпты (python-имена, не алиасы
      шаблона). `options` задают `temperature=0` (экстракция реквизитов не
      творческая задача) и явный `num_ctx=8192`, оба настраиваются через
      `OLLAMA_TEMPERATURE`/`OLLAMA_NUM_CTX`. Проверено вживую на локальной
      Ollama (`qwen2.5:3b`) — все 16 полей возвращаются верно с новой схемой.
- [x] **Загруженный файл больше не переживает обработку в веб-ветке.**
      `finally` вокруг `run_pipeline` в `/upload` чистит файл в
      `UPLOAD_FOLDER` и при успехе, и при ошибке pipeline — API-ветка
      (`routes_upload.py`) была устроена так с самого начала, через
      `NamedTemporaryFile` + `unlink`, веб-ветка была исключением.
- [x] **Таблицы в PDF больше не дублируются.** `page.extract_text()` уже
      включает содержимое ячеек в общий поток текста в порядке чтения, а
      `extract_tables()` добавлял то же самое ещё раз отдельным блоком — вход
      LLM раздувался вдвое, а regex находил каждое значение дважды. Теперь
      таблицы находятся заранее через `find_tables()`, их прямоугольники
      исключаются из текста через `outside_bbox()` перед `extract_text()`, а
      структурные `" | "`-блоки собираются из `table.extract()` отдельно.

**Результат:** 553 → **561 тест**, покрытие 95.13% при пороге 93, `ruff` и
`black` чисты.

### Э15. Спринт 3 разбора пайплайна: качество OCR и наблюдаемость *(сделано 04.09.2026)*

Продолжение Э13/Э14. Из четырёх пунктов «тюнинга Tesseract», намеченных
после спринта 1, в этот эпик вошли два — эмпирическая проверка перед
реализацией показала, что оставшиеся два были бы либо бесполезны, либо
вредны. Решения по обоим задокументированы ниже, а не просто пропущены.

- [x] **Адаптивная бинаризация по методу Оцу вместо фиксированного порога
      170.** Новый модуль `app/ocr/image_preprocessing.py` вычисляет порог по
      гистограмме самого изображения (256 корзин, без numpy — только
      Pillow). Подключено в `image_ocr_extractor.py`; в
      `pdf_ocr_extractor.py` бинаризации не было и не стало — у
      растеризованного PDF другой профиль шума, и менять то, что не вызывало
      проблем, нет оснований.
- [x] **Устранение мелкого наклона фото документа — методом проекционного
      профиля, а не через OSD.** Первоначальный план («deskew через
      `pytesseract.image_to_osd()`») оказался неверным при проверке: на
      синтетическом скане, наклонённом на 0.4°, OSD стабильно возвращает
      `Rotate: 0` — эта функция находит только грубую ориентацию страницы
      (0/90/180/270), а не единицы градусов мелкого наклона от съёмки с рук.
      Вместо неё — перебор углов на уменьшенной копии изображения с поиском
      угла, дающего самый «острый» построчный профиль яркости; подключено в
      оба OCR-экстрактора.
- [x] **Время по этапам и причина `needs_review`** (остаток Э12).
      `duration_ms` — в каждой строке лога от шага 2 до шага 7 и в обоих
      `processing_meta`; `total_duration_ms` — в финальной строке «Pipeline
      completed»; `review_reasons` (поле `ValidationReport`, существовавшее с
      Э3, но никогда никуда не логировавшееся) — в строке «Step 7/9
      validation done».

**Рассмотрено и отклонено:**

- **Отсечение слов по `conf` при сборке строк.** Идея заключалась в том,
  чтобы отбрасывать низкоуверенные токены OCR как шум. Проверка на реальной
  выдаче Tesseract на фикстуре проекта показала обратное: низкую уверенность
  получают не только шумовые токены, но и корректно распознанные метки полей
  (`КПП` — уверенность 46 из 100, при том что слово распознано верно
  побуквенно), от которых fallback-regex зависит, чтобы найти значение по
  метке. Фильтрация по порогу уверенности рисковала не убрать шум, а сломать
  рабочую экстракцию — отклонено без реализации.
- **Исправление цифр по контрольным суммам подбором OCR-похожих цифр.** В
  проекте уже есть `fold_numeric_confusables()` — свёртка визуально
  идентичных символов (`O`↔`0`, `I`↔`1`), однозначная в буквальном смысле:
  эти символы неотличимы по начертанию. Подбор цифра-к-цифре — другая по
  природе задача: `0`↔`8`, `5`↔`6` и подобные путаницы зависят от шрифта и
  качества скана, а не от формы символа, и при нескольких кандидатах,
  проходящих контрольную сумму, выбор одного из них — это не нормализация, а
  инференс с реальным риском ложного результата. Для настолько
  чувствительного класса данных, как банковские реквизиты и ИНН, это
  продуктовое решение, а не только инженерное, и без набора реальных сканов
  с типичными цифровыми ошибками OCR для проверки принимать его в одиночку
  неправильно — отклонено без реализации, задача остаётся открытой в таблице
  «Осталось из разбора».

**Результат:** 561 → **575 тестов**, покрытие 95.17% при пороге 93, `ruff` и
`black` чисты. Проверено вживую на реальном Tesseract: `logs/app.log`
показывает `duration_ms` на каждом шаге и читаемые `review_reasons`.

### Э16. Спринт 4 разбора пайплайна: инструмент замера качества *(сделано 04.09.2026)*

Единственный пункт эпика Э11, который нельзя было закрыть без входных данных
от автора, — не сам факт замера, а конкретные цифры на конкретных
документах. Инструмент построен и проверен на синтетике первым; реальные
документы для замера нашлись в `uploads/` — карточки контрагентов,
накопленные там за время использования приложения (включая артефакты
незакрытого до Э14 бага «файл не удаляется после обработки», см. Э14).

- [x] **`app/services/accuracy_service.py`.** Сравнение эталона со значением,
      которое вернул pipeline, поле за полем — пять исходов: `match`,
      `mismatch`, `missing` (эталон непустой, извлечено пусто — не то же
      самое, что неверное значение), `correct_empty` (поле действительно
      отсутствует в документе) и `false_positive` (поле отсутствует, но
      pipeline что-то подставил — опаснее обычного mismatch). `correct_empty`
      намеренно исключён из знаменателя точности по полю: иначе поле,
      отсутствующее почти во всех документах, выглядело бы «стопроцентно
      точным», хотя по нему ни разу не проверялось, находит ли pipeline
      значение, когда оно есть, — ровно та слепая зона `fill_rate`, из-за
      которой эта метрика вообще понадобилась.
- [x] **`scripts/measure_accuracy.py`.** Тонкая CLI-обвязка по образцу
      `batch_process.py`: для каждого документа в папке ищет рядом
      `<имя>.expected.json` с эталонными значениями 16 полей, прогоняет через
      pipeline, печатает таблицу точности по каждому полю и сохраняет
      JSON-отчёт в `exports/`. Документы и эталоны в Git не попадают
      (CLAUDE.md).
- [x] **Проверено вживую целиком.** Синтетическая карточка (вне репозитория,
      не коммитилась) прогнана через реальную Ollama; отчёт корректно
      показал 100% на большинстве полей и осмысленно отчитался о
      расхождениях там, где сам эталон был подготовлен неточно (например,
      номер телефона в другом форматировании, чем у pipeline) — то есть
      механизм сравнения работает так, как задуман.
- [x] **`docs/extraction-notes.md` приведён в соответствие с Э13–Э15** —
      раздел «Как измерять качество» ссылается на готовый инструмент вместо
      «пока не измерено», таблица правил `merge_llm_and_fallback` обновлена
      под признак «загрязнения» из Э13 (раньше в ней всё ещё было устаревшее
      правило «более длинное значение побеждает»), список «куда смотреть
      дальше» отмечает закрытые в Э13/Э15 пункты.
- [x] **Сам замер на реальных документах.** 18 карточек контрагентов —
      15 в `uploads/реквизиты/`, 3 в `uploads/` (PDF, DOCX, фото телефоном);
      пять файлов в `.doc`/`.pages` пропущены — эти форматы pipeline не
      поддерживает (`.doc` — старый бинарный формат Word, `python-docx` его
      не открывает; находка сама по себе). Эталон подготовлен вручную чтением
      каждого документа. `*.expected.json` остаются рядом с документами в
      `uploads/` — уже целиком в `.gitignore`, в Git не попадают — и пригодны
      для повторного «до/после» замера на любом будущем изменении.

      **Общая точность: 56.2%** на обеих папках (61 сравнённое поле-документ
      каждая). Сильные поля — `ogrn`, `checking_account`,
      `correspondent_account` (70–100%), `inn`/`kpp`/`bik` (79–87%). Слабые —
      `bank_name` (21–33%), `phone` (0–33%), `postal_address` (0–11%).

      Разбор расхождений по слабым полям показал: **это не только слепая
      зона распознавания, но и слепая зона самого замера.** Часть
      «расхождений» — не ошибки экстракции, а различия в форматировании,
      которые `compare_field()` (Э16) справедливо ловит, но которые не
      являются реальным браком:
        - `phone` в LLM-пути не проходит через `_normalize_phone()` (она
          есть только в regex-слое) — модель возвращает телефон в исходном
          форматировании документа (`8 (8734) 72-20-47` вместо
          `+78734722047`). Промпты не просят нормализовать телефон, в
          отличие от ИНН/КПП/счетов, где явное требование «только цифры»
          есть.
        - `bank_name` — кавычки `« »` vs `" "` (LLM меняет стиль кавычек) и
          порядок слов в `legal_address` (регион в начале или в конце) —
          формально mismatch при побайтовом сравнении, по содержанию верно.
        - `company_name`: 3 false_positive из-за того, что в эталоне эти
          документы содержали только краткое имя («ООО Х»), а LLM
          самостоятельно и обоснованно развернула его в полную форму —
          ограничение методики подготовки эталона, а не баг pipeline.

      Настоящих находок тоже несколько:
        - **`bank_name` систематически теряет номер отделения банка.**
          На двух независимых документах (КОРА, Энергоресурс) LLM вернула
          «СТАВРОПОЛЬСКОЕ ОТДЕЛЕНИЕ ПАО СБЕРБАНК» вместо «...ОТДЕЛЕНИЕ
          №5230 ПАО СБЕРБАНК» — обрезала номер отделения. Для платёжного
          документа это существенно.
        - **`postal_address` иногда содержит осиротевший `|`** в начале
          значения (например, `| 368006, Республика Дагестан...`) —
          артефакт табличного разделителя, который `_LABEL_TAIL` (Э13)
          чистит не на всех путях извлечения этого поля.
        - **`postal_address` иногда обрезан агрессивнее ожидаемого**
          (`район, с.п. Аллеройское, с. Аллерой, ул.` вместо полного адреса
          с регионом, номером дома) — на одном документе (Энергоресурс).
        - **`qwen2.5:3b` иногда искажает слова даже на чистом
          цифровом (не сканированном) тексте** — «Хасавт» вместо
          «Хасавюрт» на PDF с текстовым слоем, без OCR в пути вовсе.
          Отдельное подтверждение вывода из ROADMAP §«Что решено не
          делать»/рекомендаций аудита: модель 3B — нижняя граница
          работоспособности, `qwen2.5:7b-instruct` может дать заметно
          устойчивее результат.
        - **Один документ (ООО «НЕГА») получил в поле `inn` расчётный
          счёт из 20 цифр** — `validate_inn` корректно поймал это как
          жёсткую ошибку («wrong length: 20, expected 10 or 12»), но сам
          факт попадания говорит о слабом контекстном разделении полей на
          этом конкретном документе (PDF маршрутизирован в OCR-ветку,
          хотя визуально выглядит как цифровой PDF — отдельный повод
          присмотреться к `_detect_pdf_type()`).

      Отчёты — `exports/accuracy_report_real_reквизиты.json` и
      `exports/accuracy_report_real_root.json` (не коммитятся).

**Результат:** 575 → **590 тестов**, покрытие 95.28% при пороге 93, `ruff` и
`black` чисты. Плюс первый реальный замер качества за всю историю проекта.

### Э17. Спринт 5 разбора пайплайна: три находки реального замера *(сделано 04.09.2026)*

Три конкретные, воспроизводимые находки из Э16 — причины найдены прямым
чтением исходного текста, который дошёл до regex-слоя на конкретных
документах, не гаданием.

- [x] **Граница слова у меток полей.** `_extract_from_partner_card()` ловил
      подпись «Банк» через `startswith("банк")` без проверки границы слова —
      срабатывало и на «Банковские реквизиты» (слово начинается с тех же
      букв, но это не подпись поля). Строка нарезалась с четвёртого символа,
      и в `bank_name` попадал обрывок «овские реквизиты | ...». Новый
      `_starts_with_label()` требует разделитель или конец строки сразу
      после метки; применён и ко второму циклу (`strict_inline_fields`), где
      тот же паттерн потенциально бил бы по коротким меткам («инн», «бик»,
      «кпп»). Тот же класс бага нашёлся и в `_extract_bank_name()` — она уже
      верно отбирала строку по признаку «банк без бик/счёта», но никогда не
      отрезала саму подпись поля перед значением; новая `BANK_LABEL_RE`
      делает это перед возвратом.
- [x] **Осиротевший `|` в `postal_address`.** `_extract_postal_address()`
      отрезал подпись поля регуляркой до `[:\s]*`, не включая `|` —
      разделитель соседних ячеек PDF-таблицы (Э13). В значении оставался
      осиротевший `|` в начале, когда pdfplumber склеивал ячейки одной
      строки. То же — в ветке «отделение почтовой связи», которая раньше
      вообще не отрезала подпись.
- [x] **Нормализация телефона независимо от источника.**
      `_normalize_phone()` применялась только внутри regex-слоя
      (`_extract_phones`). Когда телефон побеждал от LLM — а промпт не
      просит нормализовать телефон, в отличие от ИНН/КПП/счетов, — в
      merged-результате оставалось исходное форматирование документа.
      Функция идемпотентна на уже нормализованном значении, поэтому
      применена один раз после merge в `merge_llm_and_fallback()`,
      независимо от источника.

### Э21. Спринт 8: повторное распознавание числовых полей — рассмотрено и отклонено *(05.09.2026)*

Пункт 3 из «С чего продолжить» (см. ниже) — единственный оставшийся пункт
разбора пайплайна, требовавший новой архитектуры. Четыре последовательные
попытки за один день, каждая проверена реальным замером field-level accuracy
на тех же 15 документах (Э16), ни одна не превзошла базовую линию без
какого-либо rerun (**57.6%**):

| Версия | Точность | Механизм |
|---|---|---|
| Sweep по плотности цифр, баг с ОКТМО | 56.7% | `is_numeric_candidate` по всей строке — метка кода классификатора («ОКТМО:...») проходила кандидатом, whitelist стирал метку, менялся контекст для LLM |
| Sweep, метки классификаторов исключены | 57.6% | Регрессия устранена, но и пользы на цифрах не появилось — числовые поля не изменились ни на документ |
| Allowlist по метке (ИНН/КПП/БИК/ОГРН/р-с/к-с), bbox всей строки | 55.3% | Регион для whitelist-прогона включал слово-метку («БИК банка 040 702 760») — Tesseract с `tessedit_char_whitelist` был вынужден впихнуть буквы метки в цифры |
| Allowlist по метке, bbox только «цифровых» слов (`image_to_lines_with_word_boxes`) | 56.2% | Слово-метка больше не попадает в регион, но нашлись ещё два независимых источника вреда (ниже) |

**Находки, приведшие к каждой следующей итерации:**

1. **`LABEL_WORDS` как denylist не знал про коды классификаторов** (ОКПО/
   ОКАТО/ОКТМО/ОКОГУ/ОКФС/ОКОПФ/ОКВЭД) — строка вида «ОКТМО:07727000»
   проходила «числовым кандидатом» по плотности цифр.
2. **Density-эвристика (`is_numeric_candidate`) отсекала почти все реальные
   числовые строки** — на 129 строках из 5 реальных фото нашёлся 1
   кандидат: guard на внутренние пробелы (задуманный против склейки ДВУХ
   разных чисел) на практике отсекал ОДНО число, раздробленное OCR-шумом на
   несколько «слов». Заменён на подсчёт максимальных цифровых пробегов —
   решило и заодно поймало слияние через `/` без пробела («ИНН/КПП
   0603022879/060301001» — два числа одним токеном по пробелу).
3. **Переход на allowlist по метке** (трогаем строку только если в ней есть
   ИНН/КПП/БИК/ОГРН/р-с/к-с) убрал целый класс рисков denylist-подхода
   (коды классификаторов, несвязанные строки вроде дат — «Уведомление... от
   12.07.2023 №701847440» — никогда не попадают в allowlist), но bbox брался
   на всю строку целиком → регресс хуже базовой линии (находка 4).
4. **whitelist-прогон bbox всей строки заставляет Tesseract впихивать буквы
   метки в цифры.** Строка «БИК банка 040 702 760» после прогона превращалась
   в мусор — символы «БИК банка» тоже приходилось classify'ить как какую-то
   цифру, раз алфавит сужен до `0123456789`. Добавлен
   `TesseractBackend.image_to_lines_with_word_boxes()` — геометрия отдельных
   слов, регион строится только из слов с высокой долей цифр
   (`_WORD_DIGIT_DENSITY_MIN = 0.8`, строже порога для целой строки — иначе
   слово «ИНН7744012347», метка приклеенная к числу без пробела, тоже
   считалось бы «цифровым»).
5. **Даже после word-level фикса нашлись ещё два независимых источника
   вреда:** короткая метка `"рс"` (сокращение «р/с») ложно совпадала с
   ПОДСТРОКОЙ обычных слов — «Пяти**горс**к» — и код обрезал текст адреса
   посреди слова, приклеивая туда цифровой мусор; вдобавок whitelist-прогон
   МАЛЕНЬКОГО обрезанного региона иногда распознавал **другие**, не более
   верные цифры, чем исходный полноконтекстный проход («040702760» →
   «14070760» — не опечатка на 1 символ, а другое число), вероятно из-за
   потери контекста для сегментации строк и неточных границ у
   `image_to_data`-bbox отдельных слов.

**Итоговое решение: подход отклонён.** Четыре разных дизайна одной и той же
идеи («обрезать регион, распознать заново с ограниченным алфавитом») дали
четыре разных класса порчи данных и ни разу не показали измеримого выигрыша
на реальных документах. Это не серия мелких багов, а сходящийся результат:
для Tesseract-выдачи с её word-level `image_to_data` риск (потеря контекста,
неточные границы, слово-метка в bbox) стабильно перевешивает пользу.

**Что осталось из инфраструктуры (сознательно, не мусор):**
- `TesseractBackend.image_to_lines_with_word_boxes()` /
  `OcrBackend.image_to_lines_with_word_boxes()` — общего назначения геометрия
  отдельных слов, не привязана к конкретной стратегии распознавания;
  `image_to_lines_with_boxes()` теперь построен поверх неё (тот же результат,
  один источник правды вместо дублирования логики объединения bbox).
- Кеш `easyocr.Reader` в `EasyOcrBackend.__init__` (`_reader_cache`) — снимает
  реальную стоимость (повторная загрузка весов модели на каждый документ),
  не имеет отношения к отклонённой идее.

**Что удалено:** `app/ocr/numeric_rerun.py`, `app/ocr/labeled_numeric_rerun.py`
и их тесты; `OcrBackend.recognize_region()` (база, Tesseract, EasyOCR) и его
тесты; `get_numeric_rerun_backend()`/`settings.numeric_rerun_backend` (гибрид
«структура одним бэкендом, числа — другим») и их тесты — вся эта
инфраструктура существовала только ради отклонённого механизма.

**Результат:** код вернулся к состоянию «Tesseract без какого-либо rerun»,
измеренному в 57.6% (Э16/Э17/Э18 baseline). Полный `pytest` зелёный, `ruff` и
`black` чисты.

## 5. Что решено не делать

- **Внешние LLM-провайдеры** любого вида, включая прокси к OpenAI.
- **Справочники ФИАС/КЛАДР и геокодирование** для проверки адресов — валидатор
  адреса работает только на эвристиках, без сети.
- **Контрольная сумма КПП** — её не существует; проверка только структурная.
- **Обязательность почтового индекса** — его отсутствие не создаёт даже warning.
- **Docker в любом виде** (Р6) — включая «вариант B» с контейнером Ollama в
  compose. Ollama ставится на хост как обычное приложение. Вернуться к вопросу
  только если проект будут разворачивать как сервер для нескольких человек.
- **Упаковка в `.exe`** (PyInstaller и аналоги) и **нативное окно**
  (pywebview/Qt) — при Р7 достаточно локального сервера и браузера. Упаковка
  вдобавок упирается в `easyocr`/`torch` (~2 ГБ) и внешние бинарники Tesseract
  и Poppler.
