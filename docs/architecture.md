# Архитектура

Документ описывает, как устроено приложение и почему устроено именно так.
Актуален на 23.08.2026.

Общий обзор проекта — в [README](../README.md), план работ — в
[ROADMAP](../ROADMAP.md), обязательные правила — в [CLAUDE.md](../CLAUDE.md).

---

## Что определяет все решения

Три ограничения, из которых следует почти вся архитектура:

1. **Реквизиты не покидают машину.** Отсюда: только локальный Ollama, никаких
   CDN в шаблонах, `127.0.0.1` вместо `0.0.0.0`, отсутствие внешних справочников
   для проверки адресов и банков.
2. **Распознавание не бывает идеальным.** Отсюда: review-форма как обязательный
   шаг, разделение «пусто» и «введено неверно», сохранение `raw_value` рядом с
   нормализованным значением, warning-и, которые не блокируют.
3. **Приложение локальное и однопользовательское.** Отсюда: результаты живут в
   словаре процесса, а не в БД; нет очередей, воркеров и авторизации.

## Слои

```
app/
├── main.py          фабрика Flask-приложения (единственная)
├── config.py        pydantic-settings, читает .env
├── dependencies.py  проверка загружаемого файла
│
├── web/             HTML-интерфейс: загрузка, review-форма, /generate
├── api/             JSON API: /api/health, /api/extract, /api/download
│
├── services/        оркестрация
├── extractors/      извлечение текста из конкретного формата
├── ocr/             интерфейс OCR-бэкенда, Tesseract, EasyOCR, фабрика
├── llm/             интерфейс LLM-клиента, mock, Ollama, промпты
├── validators/      по одному модулю на реквизит + кросс-проверки
├── exporters/       JSON, XLSX, заполнение DOCX-шаблона
├── schemas/         pydantic-модели, общие для всех слоёв
└── core/            константы, enum'ы, исключения, нормализаторы строк
```

Зависимости направлены внутрь: `web` и `api` знают о `services`, `services` —
об `extractors`/`llm`/`validators`/`exporters`, а `core` и `schemas` не знают ни
о ком. Обратных импортов нет.

## Основной путь: pipeline

`app/services/pipeline_service.py::run_pipeline()` — единственный оркестратор.
Оба интерфейса, веб и API, зовут его.

```
файл
  │
  ├─ 1. DocumentInput ──── sha256, расширение, MIME
  │
  ├─ 2. routing_service ── DOCX │ PDF-текст │ PDF-скан │ изображение
  │                             └─ unsupported → UnsupportedFileTypeError
  │
  ├─ 3. text_extraction_service ── диспетчер, лениво импортирует нужный
  │        ├── docx_extractor        python-docx
  │        ├── pdf_text_extractor    pdfplumber
  │        ├── pdf_ocr_extractor     pdf2image → OCR-бэкенд
  │        └── image_ocr_extractor   PIL-предобработка → OCR-бэкенд
  │
  ├─ 4. text_normalization_service ── чистка текста
  │        └─ при ocr_used=True дополнительно: склейка цифр
  │           в номерах, отделение блока классификаторов
  │
  ├─ 5. LLM ── Ollama или mock
  │        └─ профиль промпта: image для OCR, prompt_version для остального
  │
  ├─ 6. fallback_regex_service ── добор полей регулярками
  │        └─ merge_llm_and_fallback() → значения + карта источников
  │
  ├─ 7. validation_service ── 16 полей + кросс-проверки
  │
  ├─ 8. экспорт ── только если persist=True (по умолчанию нет)
  │
  └─ 9. PipelineResult
```

### Почему нормализация зависит от источника текста

Для распознанного текста включается склейка цифр, разорванных пробелами
(`ИНН 7744 012347` → `ИНН 7744012347`). Для документа с текстовым слоем это
делать **нельзя**: там пробелы внутри чисел осмысленны — `12 05 2026` это дата,
и склеивать её нечего.

Поэтому склейка ограничена строками, где есть метка реквизита, и включается
только при `ocr_used=True`.

### Почему у OCR отдельный профиль промпта

Распознанный текст ломается предсказуемым образом: цифры с пробелами внутри,
слитные строки, подмены `О`→`0`. Профиль `image` в `llm/prompts.py` объясняет
это модели прямо. Профили `v1`/`v2`/`v3` различаются по типу документа и размеру
модели и для OCR не подходят.

## Валидация

### Контракт `FieldValidation`

Ключевая модель всего приложения (`schemas/validation.py`):

| Поле | Смысл |
|------|-------|
| `raw_value` | Что пришло. Никогда не меняется, показывается в форме |
| `normalized_value` | Прозрачная нормализация: пробелы, регистр, однозначные OCR-подмены |
| `is_missing` | Не заполнено. Это **не** то же, что заполнено неверно |
| `reason` | Жёсткая ошибка. Блокирует `/generate` без `confirm_invalid` |
| `warning` | Показывается рядом с полем, генерацию не блокирует никогда |

Разделение `is_missing` и `valid=False` — не формальность. Пустое поле и поле с
опечаткой требуют от пользователя разных действий, и смешивать их в «невалидно»
значит заставлять его гадать.

### Что жёсткая ошибка, а что предупреждение

Правило: **ошибка — это то, в чём мы уверены**. Неверная контрольная сумма ИНН
или длина БИК в 5 знаков — точно ошибка. Нетипичный префикс или несошедшийся
контрольный ключ счёта — повод посмотреть, но не повод блокировать: справочники
меняются, а человек видит исходное значение.

| Проверка | Результат |
|----------|-----------|
| Контрольная сумма ИНН, ОГРН | жёсткая ошибка |
| Длина и состав символов БИК, счетов, КПП | жёсткая ошибка |
| Структура КПП (4 цифры + 2 цифры/буквы + 3 цифры) | жёсткая ошибка |
| Префикс БИК `04`, счетов `40`/`30` | предупреждение |
| Контрольный ключ БИК↔счёт (ЦБ РФ № 515) | предупреждение |
| ИНН из 12 цифр вместе с КПП | предупреждение |
| Расхождение фамилии в полном и кратком ФИО | предупреждение |
| Значение не похоже на адрес | предупреждение |
| Отсутствие необязательного поля | не ошибка вовсе |

У КПП контрольной суммы нет и не будет — только структурная проверка.

### Контрольный ключ счёта

Методика ЦБ РФ № 515 от 08.09.1997. К 20 цифрам счёта спереди дописывается
трёхзначный «условный номер банка»:

- расчётный счёт — `БИК[6:9]`;
- корреспондентский — `"0" + БИК[4:6]`.

Ключ сходится, если сумма произведений всех 23 цифр на веса
`7,1,3,7,1,3,…` (взятых по младшему разряду) кратна 10. Алгоритм сверен с
четырьмя публичными тест-векторами, они зафиксированы в
`tests/test_validators_bik_account.py`.

### Обнуление невалидных значений

`validate_requisites()` обнуляет в `data` поля, не прошедшие проверку, чтобы
заведомо неверное значение не попало в шаблон. Исходное при этом **не теряется**:
оно остаётся в `FieldValidation.raw_value`, и review-форма подставляет в поле
именно его. Без этого пользователь видел бы пустую строку вместо того, что нужно
исправить.

## Веб-слой

- `GET /` — загрузка файла.
- `POST /upload` — прогон pipeline, рендер review-формы.
- `POST /generate` — заполненный DOCX.

`_build_review_rows()` собирает 16 строк формы: подпись, значение, ошибка,
предупреждение, источник значения (`llm` или `regex`). Подпись ОГРН/ОГРНИП
выбирается по длине значения.

### Поведение `/generate`

| Ситуация | Что происходит |
|----------|----------------|
| Всё валидно | 200, DOCX вложением из `BytesIO` |
| Жёсткая ошибка без `confirm_invalid` | 422, форма с сохранёнными значениями |
| Жёсткая ошибка с `confirm_invalid` | 200, документ с этим значением как есть |
| Незаполненное поле | не блокирует, даже если поле обязательное |
| Предупреждение | не блокирует никогда |
| Нет `shablon.docx` | 503 с понятным текстом, не 500 |

Документ собирается из значений формы, а не из очищенных данных: при
`confirm_invalid` пользователь ожидает увидеть в файле именно то, что подтвердил.

## Файлы на диске

По умолчанию **обработка не оставляет следов**. `persist_artifacts` выключен,
`run_pipeline(..., persist=False)` не пишет ни распознанный текст, ни результаты,
и даже не создаёт папки. Поля `*_path` в результате остаются `None`.

Сохранение включают там, где оно и есть смысл команды — в CLI и пакетной
обработке. `/api/download` собирает запрошенный формат на лету из результата в
памяти: для этого у экспортёров есть варианты `build_json_payload()`,
`export_xlsx_to_bytes()`, `fill_template_to_bytes()`.

## Шаблон DOCX

Плейсхолдеры — имена в одинарных кавычках: `'FULL_ORG_NAME'`, `'INN'`. Работают
в параграфах и в ячейках таблиц. Плейсхолдер, разбитый Word'ом на несколько
runs, обрабатывается корректно: текст параграфа собирается целиком, заменяется и
кладётся в первый run.

Соответствие полей и плейсхолдеров задано в `RequisitesData.to_template_dict()`.

## Точки расширения

| Задача | Куда смотреть |
|--------|---------------|
| Новый формат документа | `core/enums.py`, `routing_service.py`, новый модуль в `extractors/`, ветка в `text_extraction_service.py` |
| Новый OCR-бэкенд | реализовать `OcrBackend`, зарегистрировать в `ocr/factory.py` |
| Новый LLM-провайдер | **только локальный.** Реализовать `BaseLLMClient`, добавить в `LLMProvider` и `_build_llm_client()` |
| Новое поле реквизитов | `RequisitesData`, плейсхолдер в шаблоне, валидатор, `FIELD_LABELS`, `run_field_validators()` |
| Новое правило валидации | модуль в `validators/`, подключить в `validation_service.py` |

## Осознанные ограничения

- **Нет БД.** Результаты API живут в словаре процесса и теряются при
  перезапуске. Для локального однопользовательского приложения этого достаточно.
- **Нет очередей.** Обработка синхронная, пользователь ждёт ответа.
- **Нет справочников.** Ни ФИАС, ни КЛАДР, ни список банков ЦБ — любая сверка
  означала бы сетевой запрос с реквизитами.
- **Нет авторизации.** Приложение слушает только localhost.
- **Версии зависимостей не закреплены** — известная проблема, см. ROADMAP.
